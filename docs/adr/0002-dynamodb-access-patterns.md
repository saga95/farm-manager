# ADR-0002: Single-table DynamoDB and access patterns

- **Status:** Accepted (2026-10-03)
- **Issue:** #19 · **SRS:** §26.3, §41.11, §27, DQ-010

## Context

- The SRS requires an access-pattern-first DynamoDB design (§41.11), and no index may let a request bypass tenant authorization.
- With custom Lambda operations (ADR-0001), Amplify's generated per-model tables give little benefit, and they cost us control over keys and transactions.
- Inventory and round completion need **multi-item atomic writes** (`TransactWriteItems`), and that's simplest within one table.

## Decision

**One table, `FarmData`**, defined with CDK in `amplify/backend.ts` (`backend.createStack('data-stack')`). It has:

- **on-demand billing**, **point-in-time recovery on** (SRS §25.4), and deletion protection on the prod branch;
- keys: `PK`, `SK` (strings), plus **GSI1** (`GSI1PK`, `GSI1SK`) and **GSI2** (`GSI2PK`, `GSI2SK`);
- a `tenantId` attribute on **every** item, re-checked after reads (ADR-0001 §3);
- every partition key **starts with `T#<tenantId>`** and every GSI1 key **starts with `T#<tenantId>`**, so a query can't span tenants.

GSI2 is the only index whose key isn't tenant-prefixed. It serves **get by ID**, and results are always tenant-checked.

IDs are **ULIDs**, generated by the client for field records (ADR-0004), so they sort by time. Dates in keys are ISO `YYYY-MM-DD`.

Notes:

- **Tenants of a user:** `GSI1PK = U#<userId>` is the one GSI1 key without a tenant prefix. It's allowed because it returns only the **caller's own** memberships, and the handler forces `userId = sub`.
- **Due-soon:** with about 50–300 trees per farm, the due-soon list is computed **on read**. Query the farm's trees by status (GSI1). Each tree item has a denormalized `prediction` snapshot (`nextEstimate`, `window`, `confidence`, `methodVersion`) that is rewritten whenever its harvests change. Then sort in memory. A dedicated index is deferred until a tenant has more than about 2,000 trees.
- **Sale lines** are embedded in the Sale item (under 20 lines, under 400 KB). **Produce stock** is the sum of transactions (CALC-010). The batch keeps a cached `available` and `availableByState`, updated **in the same transaction** as each txn, and verified by a reconciliation test.

### §41.11 access patterns → keys

| Access pattern                   | How                                                                          |
| -------------------------------- | ---------------------------------------------------------------------------- |
| Farms by tenant                  | `PK=T#t`, `SK begins_with FARM#`                                             |
| Zones and spaces by farm         | `PK=T#t#F#f`, `SK begins_with ZONE#` / `SPACE#`                              |
| Trees by farm and status         | GSI1 `T#t#F#f#TS#PRODUCING`                                                  |
| Tree by farm and code            | `PK=T#t#F#f`, `SK=TREE#C-012` (GetItem)                                      |
| Rounds by farm and date          | `PK=T#t#F#f`, `SK between ROUND#d1 and ROUND#d2`                             |
| Harvest timeline by tree         | `PK=T#t#TREE#id`, `SK begins_with H#`                                        |
| Harvests in a round              | GSI1 `T#t#R#roundId`                                                         |
| Sample history by tree           | `PK=T#t#TREE#id`, `SK begins_with S#`                                        |
| Due and predicted trees          | trees by status + `prediction` snapshot, sorted in memory                    |
| Cycles by farm, space or status  | `PK=T#t#F#f SK begins_with CYCLE#`; GSI1 `T#t#SPACE#s`                       |
| Activities and harvests by cycle | `PK=T#t#C#c`, `SK begins_with A#` / `GH#`                                    |
| Batches by farm, crop or state   | `PK=T#t#F#f SK begins_with BATCH#<crop>`; GSI1 `…#STOCK` for available stock |
| Txns by batch and date           | `PK=T#t#B#b`, `SK begins_with TX#`                                           |
| Inventory items                  | `PK=T#t`, `SK begins_with ITEM#`                                             |
| Buyers by tenant                 | `PK=T#t`, `SK begins_with BUYER#`                                            |
| Sales by farm, date or buyer     | `PK=T#t#F#f SK between SALE#…`; GSI1 `T#t#BUYER#b`                           |
| Get any entity by ID             | GSI2 `ID#<id>`, then the tenant check                                        |

## Consequences

- ✅ Tenant isolation is built into every key, and atomic multi-item writes are available.
- ✅ Deployment portability: the table name comes from CDK outputs, and a per-tenant export is `Query PK begins_with T#t` plus GSI2, which fits the topology note in ENVIRONMENTS_AND_RELEASES.
- ⚠️ No Amplify-generated model client. The typed client is generated from the **custom operations** in the schema instead.
- ⚠️ Changing key formats later needs a migration. Keep key builders in one module (`src/domain/keys.ts`), and unit-test them.
- ⚠️ Hot partitions are not a concern at this scale (one farm writes about 10 items per minute at peak).
